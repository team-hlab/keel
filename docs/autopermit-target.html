The key abstraction: adapters normalize each platform's raw tool names into capability categories (READ / WRITE / OTHER) — so the core reasons about "a file write", never about apply_patch vs Edit vs Antigravity's names. That is what lets one policy serve three agents.

The only two contracts the core knows

ToolRequest (in)

capability: READ | WRITE | OTHER   # normalized
path:       str   # abs, realpath'd
raw_name:   str   # for secret basename
stage:      PRE | PERMISSION

Verdict (out)

decision: ALLOW | DENY | ASK | PASS

Layout

autopermit/ ├─ core/ # pure · platform-agnostic · the brain │ ├─ model.py ToolRequest · Verdict · Decision │ ├─ policy.py decide(req, cfg) → Verdict ← ports verbatim │ ├─ paths.py root · worktree · secret detection │ └─ config.py load autopermit.toml ├─ adapters/ # all platform variance lives here │ ├─ claude_code.py ✓ done (PreToolUse + PermissionRequest) │ ├─ codex.py + to add │ └─ antigravity.py + to add (verify schema live) ├─ config/ │ └─ autopermit.toml # ONE source of truth ├─ registrations/ # snippet each platform pastes in └─ tests/ test_policy.py
Cross-cutting rule. Read-only tools don't prompt on any platform — so secret-read confirmation must be emitted at the always-runs pre-tool stage as ASK. Therefore the PreToolUse-equivalent adapter is mandatory and load-bearing; the PermissionRequest-equivalent is an optional secondary layer that reuses the same Verdict, so the two stages can never disagree.
