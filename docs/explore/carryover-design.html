keel · feature design · status: PROPOSAL

carryover

Cross-agent session hand-off, captured automatically — below the agent.

Switch from Claude Code to Codex to Antigravity mid-task and keep your working context. keel captures the semantic spine of a session at the hook boundary, stores one tiny snapshot per repo, and injects it into whichever agent you start next — no command to remember, no per-agent skill.

1 · The problem — live context is trapped per-vendor; every switch is a cold start

The goal, the decisions, the dead-ends you already ruled out, the four half-edited files — your live session state lives inside whichever agent you happened to use. The moment you switch agents, it's gone. And you switch more than you'd think — usually involuntarily:

Limits

You hit a usage/rate cap at 70% through an auth refactor and must move to another agent to keep going. Unplanned — no chance to checkpoint.

Right tool

You run Claude + Codex + Antigravity and pick per task. Each is a silo with its own memory and config.

Stuck

One agent loops or wedges; you switch for fresh eyes — mid-task, with no clean stopping point.

Every switch then charges a cold-start tax:

① Re-brief

You retype the goal, the constraints, the decisions, by hand. costs: your time

② Re-explore

The new agent re-reads the same 50 files to rebuild state it can't see. costs: tokens + latency

③ Diverge

Blind to history, it retries an approach you already rejected — or undoes the previous agent's work, silently. costs: correctness

Why today's fixes don't close it. CLAUDE.md / AGENTS.md hold static project facts — not the live state of what you're doing right now — and they're per-vendor. Manual hand-off (savepoint) captures live state, but you have to remember to run it — which fails exactly when the switch is involuntary — and it's a per-agent skill. The gap is specific: nothing captures live session state automatically, across vendors.

Why carryover, and why keel

keel already sits below every agent as a hook shim — the one layer positioned to capture state without being asked and restore it into any agent. carryover is that: the automatic, cross-vendor version of the manual hand-off. The prior art's own verdict — "hand-off is a habit, not a technology" — names precisely what keel turns into infrastructure.

Positioning. carryover is the opposite of savepoint on every axis — and that gap is the product.

2 · Where it sits — capture is an adapter job; the store is the core

keel is ports-and-adapters. carryover adds nothing to that shape: the core wants a normalized {goal, state, result}; each adapter sources those fields however its agent allows (inline payload field vs. reading the transcript the hook points to). Variance lives at the edge, exactly like the existing parse/render split.

4 · What counts as "proper" — the schema is the filter

Don't log-then-summarize (that stores useless data by construction). Capture schema-first: write only the fields the hand-off admits; never store the rest. "Proper" is decided at write-time, not read-time.

opt-in

Ship T0+T1: prompts + mutated-files + last-answer reconstruct what / changed / where-landed with zero AI at a few KB per project. T2/T3 are upgrades, not prerequisites.

6 · Injection & safety — what keel does that the manual tools do by hand

Verification mandate

The injected digest is hypotheses, not facts. It carries an explicit directive: re-read the files, validate against code, don't trust this. Both prior-art tools insist on it.

Git-drift check free

At SessionStart keel compares snapshot vs. live branch/HEAD/working-tree. Disk state wins. savepoint does this manually at load; keel does it automatically — it already resolves root.

Redaction reuse

Run the existing secret-scan feature over anything carryover stores. keel is the policy layer; this is a one-line reuse, not new code.

Interop, not reinvention. Emit the same SAVEPOINT.md / SAVEPOINT_V1 marker savepoint already defines — so keel becomes the automatic capture engine feeding a format users can already load. Complementary, not competing.

7 · Fit & net-new work — how much is actually new

Reused as-is

  • Feature trait — carryover is one applet, like audit-log
  • audit-log's how — fail-open append, root-keyed, opt-in (drop its what)
  • runtime::find_root — repo-root keying + git-drift
  • secret-scan — redaction before store
  • engine aggregation / registry — observer returns None

Net-new

  • wire UserPromptSubmit + Stop + PreCompact into agent.rs STAGES
  • adapter parse for those payloads — inline vs transcript-read, per agent
  • carryover.rs — snapshot capture + salience gating + mutation filter
  • SessionStart inject path — digest + drift check + verification preamble
  • optional keel carryover / keel checkpoint CLI verbs

8 · Phasing

  1. Foundation — wire the 3 capture stages + per-agent parse (Codex inline, Claude/AG transcript). Tests, behind opt-in flag. spike next
  2. Store — carryover.rs: T0+T1 snapshot, mutation filter, secret-scan, overwrite-in-place. then
  3. Inject — SessionStart digest + git-drift + verification mandate; keel carryover. then
  4. Enrich — T2 PreCompact harvest + keel checkpoint; SAVEPOINT interop. later
  5. Optional — T3 LLM distill (off by default); memory read-policy (durable, not just last-session). optional

9 · Open decisions

Answer in the core?

Include the agent's answer in the cross-agent core (Claude/AG need a transcript read), or keep core = prompts + state and treat answer as a Codex-cheap enricher?

Inject = auto or confirm?

Auto-inject the digest at SessionStart, or stage it and let the user pull (keel carryover load)? Auto is seamless; confirm is safer.

Scope: hand-off vs memory?

Ship last-session hand-off only, or design the store now for durable project memory (a later read-policy on the same snapshot)?
